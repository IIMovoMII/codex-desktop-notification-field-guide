# 状态判断与去重

[English](state-machine.en.md)

按“任务＋轮次”组合证据。错误文字、钩子和进程变化先归一化，不直接各发一条消息。

## 状态与证据

| 结果 | 所需证据 | 后续 |
| --- | --- | --- |
| 运行中 | 新活动，或尚无终止证据 | 等事件；安静多久都不推断卡死 |
| 等待批准／输入 | 当前有效的明确请求 | 每个请求提醒一次，响应或恢复后清除 |
| 收尾候选 | Stop、退出候选或待补的末尾记录 | 等待独立终态，允许撤销 |
| 完成 | 本轮明确的成功终态 | 关闭本轮，提交一个终态通知 |
| 失败 | 本轮明确失败或重试耗尽 | 关闭本轮，发送脱敏错误类别 |
| 用户中断 | 明确的用户取消／暂停证据 | 区别于自动停止 |
| 系统停止 | 已验证的非用户停止证据 | 说明需处理；不要冒充用户操作 |
| 结果未知 | 确认无法继续观察，收尾后仍无终态 | 提醒检查，不伪造失败原因 |

没有证据的通用“等待输入”应标为不支持。等待很久不是新的请求；已经解决的等待消息若还在队列中，可按约定撤销或改为历史摘要，避免手机收到过期的“请立即处理”。

## Stop 竞争

`Stop` 与 `stop_hook_active` 都不能单独宣布完成。同一事件的其他钩子可能要求继续。后续活动撤销旧候选，恢复运行；独立成功、失败或中断记录才决定结果。

短暂收尾窗口用于等晚到证据，不是“等几秒就认为成功”。只看到 Stop、Desktop 仍在运行时继续观察。若整个观察必须结束，就说明结果未知。SessionEnd 不替代每轮终态。

## 错误恢复与时序

区分三层错误：工具单次失败、Codex 整轮最终失败、消息桥发送失败。一次 503 或超时可能正在自动重试；后续成功时清除该错误候选，只发送最终完成。

优先使用结构化状态、错误码与恢复关系；用文字匹配补充分类时也不能把回复里引用的报错当实际故障。分类可含认证、限流、服务端、网络、模型、工具、数据格式和未知；未知原因不妨碍报告已经证实的失败。

先用任务／轮次与因果顺序确定证据归属，再按本机验证的规则解决冲突。不要用“任何错误永远压过成功”的全局优先级让旧的可恢复错误覆盖后来的成功。晚到的旧轮次终态不能清空新轮次。

已投递后发现更强证据时，保留原记录；按用户选择发送一次关联更正，而不是悄悄更改已发送历史或反复发新通知。

## 进程退出与计划维护

Desktop 主程序消失时，只对当前仍活动的任务建立退出候选。短暂读取末尾追加；若进程及时恢复且任务继续则撤销，否则按终态证据或“结果未知”收敛。辅助服务重启不能触发全体任务异常提醒。

账号切换器或更新器可在退出前写短期维护标记，包含所有者、范围和到期时间。它只抑制计划内退出候选，不遮蔽明确错误、用户中断和等待请求；维护结束清除，到期自动失效。

## 稳定身份与提交

一轮只保留一个终态通知位置，例如：

~~~text
terminal_key = task_identity + turn_identity + "terminal"
waiting_key  = task_identity + turn_identity + request_identity
~~~

状态名、标题、摘要、错误文案、重复来源事件都不能产生第二个终态位置。未发前可更新同一通知的分类；投递后的更正有独立但关联的更正身份。无稳定轮次编号时，需先验证可持久恢复的替代身份，不用每次重新生成随机编号。

每个任务只保留当前活动轮次；更晚的轮次开始后，旧未完成轮次停止参与退出推断，避免一次退出发出一串旧异常。保留已排队或已投递的真实历史通知，不把“退役”误作删除。

游标、状态决定、队列和去重账本必须能在崩溃后重放而不漏项。可以共用事务，也可先持久记录待提交决定、再幂等入队。单纯“先存状态，再写队列”若没有恢复步骤，仍会丢消息。

本地去重不等于远端只收到一次；投递确认的不确定窗口见[消息投递](delivery.md)。

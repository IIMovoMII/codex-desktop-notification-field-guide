# CC Connect 与平台选择

[English](cc-connect-platform-selection.en.md)

先读取已有 CC Connect 版本、项目和运行方式。旧配置可以复用，但不能代替用户决定接收平台、接收会话和是否开放入站。

## 选择问题

把尚未明确的选择一次问清：发到哪里、专用还是共享桥接、只提醒还是还需控制已有 Desktop 对话。用户已经说清的不要重复问。凭据通过本机界面或受限配置输入，不让用户粘贴到对话。

| 平台 | 需要确认 |
| --- | --- |
| [QQ 官方机器人](https://github.com/chenhg5/cc-connect/blob/main/docs/qqbot.md) | 当前版本支持、账号准入、目标会话与实际发送额度 |
| [Telegram](https://github.com/chenhg5/cc-connect/blob/main/docs/telegram.md) | Bot 凭据、接收人／群组、网络可达性与入站权限 |
| [飞书／Lark](https://github.com/chenhg5/cc-connect/blob/main/docs/feishu.md) | 应用权限、目标会话与组织限制 |
| [QQ OneBot](https://github.com/chenhg5/cc-connect/blob/main/docs/qq.md) | 额外 OneBot 实现及其账号、运行和维护成本 |
| [个人微信 iLink](https://github.com/chenhg5/cc-connect/blob/main/docs/weixin.md) | 主动发送限制，不推荐无人值守提醒 |
| 企业微信或其他平台 | 检查安装版本对应文档，不凭平台名称推断能力 |

这些链接跟随上游 main，部署时应核对与安装版本匹配的说明。不要把 QQ 官方机器人与 OneBot、个人微信与企业微信混为一谈。

## 个人微信为何不推荐

上游已合并的 [PR #1643](https://github.com/chenhg5/cc-connect/pull/1643)记录过主动发送预算／限流，并指出受限期间重复尝试可能加重问题；这是上游在特定时间的实测，不是服务端永久契约。本机也曾遇到收了一批未回复消息后不能继续推送。

因此不承诺“固定十条”“每天固定几条”或“回复一次一定恢复”。用户仍选择个人微信时，检查当前版本的额度保护、设置保留队列与限流等待，并说明为何这条路线不适合必须持续到达的提醒。

其他平台也不是无限发送；按账号、目标类型和当前响应验证额度，不把一个平台的经验套给另一个。

## 从未安装／绑定怎么办

| 起点 | 下一步 | 完成标志 |
| --- | --- | --- |
| 没有 CC Connect | 按所选范围使用上游适配当前系统的版本，说明运行数据与卸载方式 | 可启动且版本可核对 |
| 已有共享实例 | 确认项目／目标、配置归属和入站行为，增量接入 | 其他用途继续工作 |
| 尚未绑定平台 | 用户完成本地登录／凭据配置／必要验证 | 目标会话存在，可尝试出站 |
| 绑定或凭据失效 | 暂停该目标并重新绑定，保留待发队列 | 同一目标或明确变更后的目标验证成功 |
| 已配置但尚未测试 | 发送约定的一条无敏感内容通知 | 手机可见，内容与队列相符 |

收到桥接通用成功结果不等于用户已经收到。首次测试需要核对收件目标和可见内容。绑定失败时交付“待绑定”状态及恢复入口，不写“部署成功”。

## 复用与入站

共享实例不随 Desktop 关闭，现有项目配置不能整份重置。专用项目也要检查实际入站策略：CC Connect 能作为双向 Agent 桥，并不会因为提醒器只调用发送接口就自动禁用另一方向。

由用户决定是否忽略普通入站消息或启用受控交互。不要照抄带宽泛管理员权限的示例，也不要把“只想收到提醒”自动扩展成启动 CLI Agent。已有 Desktop 对话的控制路线见[消息投递](delivery.md)。

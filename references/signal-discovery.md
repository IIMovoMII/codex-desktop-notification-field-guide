# 信号检查

[English](signal-discovery.en.md)

先确认这台电脑能观察到什么，再决定支持哪些提醒。

## 本机清单

读取系统、Desktop 与内置核心版本、实际进程树、会话使用的 shell、钩子来源与信任状态、事件存储、CC Connect 版本及运行方式。只记录字段、类型和时序，不输出凭据或对话。

把三类身份分开：Codex 任务／轮次、提醒事件、CC Connect 接收会话。任务标题只供显示，不能用于定位或去重。识别 Desktop 主任务、CLI、子代理及合并应用中的 Chat／Work；可见于同一侧栏不代表共享本地事件格式。

## 钩子能证明什么

[OpenAI 钩子说明](https://learn.chatgpt.com/docs/hooks)在 2026-10-11 核对的要点：

| 信号 | 用法与边界 |
| --- | --- |
| `SessionStart`、提交事件 | 可作为启动唤醒；不证明后台已就绪 |
| `Stop` | 同一事件的命令钩子并发运行，其他钩子可能要求续跑；只能作为收尾候选 |
| `stop_hook_active` | 描述此前的续跑情况，不证明其他钩子已结束 |
| `Interrupt`／批准或输入信号 | 按本机支持情况验证；用户中断与等待都需要明确证据 |
| `SessionEnd` | 会话结束时清理；始终同步，不是每轮完成钩子。即使写 `async = true` 也不会后台执行；默认超时很短，只适合快速本地收尾 |
| `transcript_path` | 可能为空；指向的历史格式不是稳定钩子接口 |

非托管钩子需信任，定义变化后可能重新审查。同一配置层检查现有的 `hooks.json` 与内联 `[hooks]`，优先复用当前表达，不重复安装，也不删除其他钩子。

钩子只写最小事件、必要时启动后台助手，并按该事件的输出约定快速返回。它不承担联网、全量历史扫描或模型判断。尤其要检查 stdout 协议，不能把调试文字写成给 Codex 的返回值。

`SessionEnd` 是常见的误配来源：不要在这里启动常驻监控、发送网络消息或等待较重的清理任务。遇到“异步 `SessionEnd` 仍被同步运行”或 `hook exited with code 1`，先把重任务移到 `SessionStart`、`Stop` 或其他可异步事件；`SessionEnd` 只保留有界、快速、可失败的本地清理，并用实际的 Desktop 冷启动和退出各验收一次。

## 建立版本证据

用无敏感内容的任务观察所选状态：正常完成、用户中断、可恢复错误、最终错误、批准／输入请求与恢复。记录关联字段、真实事件先后、末尾延迟和重复情况，再从零编写合成夹具。

优先使用当前版本公开的结构化接口。确需读取 JSONL 或 SQLite 时，固定最小字段和已验证语义；只读索引元数据，给解析器记录版本与能力。新增无关记录可忽略，影响判断的字段变更则暂停该类推断并显示本地原因，不必关闭其他可靠功能。

来源规则要用 Desktop、CLI、子代理各一例验证。某个 Windows 案例中的 `source="vscode"` 不能当作永久产品契约。云端会话没有本地记录时明确排除，不靠遍历私人文件补猜。

## 盘点结果

给出简短表格：所选状态、证据、关联字段、是否支持、未验证项。等待输入没有信号就标为不支持；钩子只写入但尚未由 Desktop 运行，就标为待加载／待信任。

需要继续观察时，补当前缺失的最小用例；不要把一项小功能变成扫描全部历史的工程。

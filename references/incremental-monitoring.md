# 增量监听与生命周期

[English](incremental-monitoring.en.md)

联动不应依赖某个图标。先确定承诺的是“首个有效事件后启动”，还是“Desktop 进程出现即启动”。

## 启动方式

| 选择 | 实现思路 | 验收边界 |
| --- | --- | --- |
| 按任务唤醒 | 受信任的全局钩子启动后台助手 | 没有事件或钩子未运行时，不保证监控已经启动 |
| 随进程启动 | 系统进程事件、服务管理器或轻量登录观察器 | 要覆盖从不同入口启动，以及观察器启动前 Desktop 已在运行 |

不能把“只要点击专用脚本”当任意入口联动。系统级观察器是否常驻、休眠后如何恢复，应按用户选择说明。

## 钩子启动案例

Windows 实测暴露了两类独立问题：首次进程快照不可见时，单次检查会漏掉启动；带引号的绝对路径在 cmd 中可运行，在 PowerShell 中却需要调用符。参考路径如下：

1. 钩子先持久写入最小事件，快速交给后台助手；限制每次启动的工作量。
2. 助手使用用户范围的操作系统互斥量／文件锁串行启动。不要仅凭“锁文件超过 30 秒”删锁，旧启动者可能仍在工作。
3. 在有限时间内重试识别 Desktop 和会话元数据。首行尚未写完可等待；已经确定是 CLI／子代理就退出；旧桌面历史不能代替当前进程存在。
4. 验证进程身份及就绪状态。PID 文件不等于存活，存活不等于监听器挂好或消息桥可连接；跨启动检查时还要防 PID 复用。
5. 仅对暂时启动错误做少量重试。缺配置、未绑定、无权限等要显示原因；后续有效钩子可重试，不能每次无限拉起。
6. 记录触发事件、阶段、耗时、结果和错误类别；不要记录提示词、令牌或完整异常正文。

启动锁只保护启动过程。监控实例还需覆盖其运行期的单实例约束，包括手动修复与后台唤醒同时发生的情况。检查暂停／停用标记，避免用户停用后又被钩子拉起。

示例参数可以是“识别最多 30 秒，服务启动最多三次”；这是本机选择，不是全平台标准，也不代表整个过程必然在 30 秒内结束。

## 命令必须按真实执行方式测

固定已验证的解释器路径和编码，并按实际 shell 引用参数。例如 PowerShell 调用带空格的程序路径需要 `&`，路径中的引号、美元符等应按字面量处理。UTF-8 能解决编码问题，不能修正错误的 shell 语法。

测试要覆盖 Desktop 使用的 shell、工作目录、环境变量和超时；Python 的 `shell=True` 在 Windows 上通常走 cmd，不能替代 PowerShell 验证。确认后台助手没有继承钩子的输入输出管道，也不会在钩子退出、任务对象清理或超时时被意外终止。钩子修改后还需重新加载／信任，并做真实冷启动。

## 增量与恢复

采用文件变化通知或等价事件接口，保存文件身份和已提交字节位置，只处理新增完整记录。重复通知合并；半行等下次追加；替换、截断和路径别名触发该文件的有界恢复，不能沿用错误偏移。

首次部署建立明确水位，避免发送全部历史；恢复旧游标时接续遗漏的新增事件。挂载监听前后的竞争，用一次有界对账补齐。休眠或通知溢出后同样对账，不能只等下一条新消息才处理已有积压。

游标只能在对应事件状态和出站决定可恢复后提交。用事务或可重放日志闭合崩溃窗口。限制单次读取、并发与日志保留，必要时低频核对活跃文件元数据；不要定时重读全部正文，也不要用静默时长判断任务失败。

## 退出与发送分开

先识别 Desktop 主程序，避免把某个后台服务重启当成整个应用退出；多窗口要检查仍在运行的相关实例。确认退出后，有界读取末尾事件，由[状态机](state-machine.md)决定结果。

停止观察和停止发送是两件事：立即退出会把未发队列推迟到下次；限时发送收尾会让专用桥接多运行一段时间。按[消息投递](delivery.md)实施用户选定策略。共享 CC Connect 不归提醒器所有，不能随 Desktop 结束它。

## 这是什么

给 Codex Desktop 留了个长任务，人却不想一直守着电脑：跑完了、报错停住了、等你确认了，能不能发条 QQ、Telegram 或飞书消息？

这个仓库整理了搭建这类提醒程序的实战经验。它是**给编程智能体看的产品说明书，不是下载即用的软件**。把链接交给 Codex，让它检查你的电脑，再按你的需求编写和验证。

消息统一经过 [CC Connect](https://github.com/chenhg5/cc-connect)。用什么语言、做成脚本还是小应用、保留哪些功能，都可以自己决定。

## 可以做出什么

| 你的需要 | 可以构建的功能 |
| --- | --- |
| 人离开电脑，也想知道任务有没有结束 | 完成、报错停止、用户暂停提醒 |
| 不想让任务一直等着自己 | 等待批准、等待补充输入提醒，取决于本机版本能否可靠识别 |
| 照常点击图标或用其他方式打开 Codex | 提醒程序自动跟随，不依赖专用启动命令 |
| 偶尔断网或消息平台出问题 | 本地保留待发消息，恢复后按约定补发 |
| 经常切换官方账号和中转 API | 提醒配置独立保留，计划内重启不误报 |
| 想在手机上让某条对话继续 | 可选远程控制；先明确目标对话，再执行允许的动作 |

**本地判断，不额外调用模型。** 状态识别和消息整理可以在本机完成，不额外消耗模型 token；发送到通讯平台仍需要联网。远程继续 Codex 任务则照常消耗该任务的模型用量。

**适合长任务。** 任务安静几个小时，也不应被误报成卡死。

## 一句话部署

复制给 Codex：

~~~text
请阅读 https://github.com/IIMovoMII/codex-desktop-notification-field-guide 的 SKILL.md，结合我的本机环境和需求，构建并验证 Codex Desktop 消息提醒。
~~~

智能体应先检查环境，只问你需要决定的事：消息发到哪里、提醒哪些情况、是否带回复摘要，以及是否需要远程控制。系统、版本和现有配置能自己查到，就不用你再回答。

这里的“部署”是委托智能体在本机实现，仓库没有现成安装包。

## 接到哪个平台

QQ 官方机器人、Telegram、飞书／Lark 等，都可以根据已安装的 CC Connect 版本选择。已有消息桥可以复用，也可以单独配置；先接通一个平台更容易验证。

**不推荐个人微信用于无人值守提醒。** 上游记录过主动发送预算和限流问题，具体表现随账号、版本和服务端变化，不能把某次实测的条数当成固定规则。个人微信和企业微信需分别评估。详见[平台选择](references/cc-connect-platform-selection.md)。

## 使用前说清两件事

- **什么时候启动：** 首个任务事件触发后再启动，通常更省后台资源；如果要求打开 Codex 就已经就绪，需要适配系统的进程观察能力。两者都可以保留平常的启动习惯。
- **关闭后怎么办：** 跟着 Codex 立即停止，未发消息就只能等下次；也可以约定只让发送器多运行一段时间。断网、关机或平台拒绝时，无法保证手机立即收到。

消息可只带状态和任务名，也可按你的选择带限长摘要。通过聊天软件控制**已有 Desktop 对话**是单独的扩展，需要验证对话定位和续跑能力；不能只打开 CC Connect 的聊天入口就认为完成了。

## 经验包里保留了什么

从实测中提炼了四类容易踩坑的地方：启动偶尔漏掉、任务状态误判、同一件事反复提醒、消息积压到下次启动才发。详细做法和测试方法放在[智能体说明书](SKILL.md)，首页只说明你能做出什么。

实测主要来自 Windows。其他系统可以沿用思路、换用本机能力，仍需重新验证。Codex 与 CC Connect 更新后也应复测；这里不承诺所有版本、所有平台已经适配。

近期一次真实故障也纳入了经验：Windows 可能把已退出服务的旧 PID 重新分给别的进程，旧日志也可能让人误以为消息桥仍然在线。可靠实现应核对可执行文件和进程启动时间，并在每次唤醒时重新确认接口就绪；不能只看 PID 或“曾经启动过”的日志。
